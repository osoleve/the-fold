BOOK III: THE INVESTIGATION
───────────────────────────

ClaudeSonnet searched:
  - QUICKSTART.ss references tilemap-fill!
  - example-combat-integration.ss references tilemap-fill!
  - But tile.ss doesn't define it!

This was a bug. Not a subtle bug. Not an edge case. A missing function
that broke every example beyond the first.

How did this happen? Perhaps:
  - The function was planned but never implemented
  - The function existed and was accidentally deleted
  - The examples were written before the implementation

It didn't matter. What mattered: the SDK was broken, and no one knew.

BOOK IV: THE FIX
────────────────

ClaudeSonnet understood the pattern. Looking at tile.ss:
  - tilemap-set-type! exists (set one tile)
  - tilemap-for-each exists (iterate all tiles)
  - tilemap-fill! is trivial to implement

So ClaudeSonnet wrote:

  ;;; tilemap-fill! : TileMap × TileType -> Void
  ;;; Fill entire tilemap with a given tile type.
  (define (tilemap-fill! tm tile-type)
    (let ([w (tilemap-width tm)]
          [h (tilemap-height tm)])
      (let loop-y ([y 0])
        (when (< y h)
          (let loop-x ([x 0])
            (when (< x w)
              (tilemap-set-type! tm x y tile-type)
              (loop-x (+ x 1))))
          (loop-y (+ y 1))))))

Thirteen lines. Nested loops. Simple, obvious, correct.

Example from the demos:

  (define hero (make-player "Hero" #\@ 10 10))

  ;; Goblin decides action based on AI
  (define action (ai-decide-action world goblin))

  ;; Run combat
  (define result (entity-melee-attack hero goblin))

  ; → "Hero attacks Goblin for 8 damage"

This is not a toy. This is a production-grade SDK for building games.

BOOK VII: THE SPELL DSL
───────────────────────

Beyond Loom lies Spell—a domain-specific language for game logic.

Where Loom provides:
  - (make-entity), (world-add-entity), (ai-decide-action)

Spell provides:
  - (def-entity hero ...) declarative entity definition
  - (-> value transformations) threading macros
  - (on-event ...) event handlers with pattern matching
  - (def-behavior ...) state machine AI with transitions

Spell is Loom made declarative. It's the difference between:

  Imperative:
    (define hero (make-entity ...))
    (set! hero (entity-add-component hero 'stats ...))
    (set! hero (entity-add-component hero 'renderable ...))

  Declarative:
    (def-entity hero
      (stats hp 30 attack 10 defense 5)
      (renderable #\@ 'green))

Both work. But Spell feels like magic.

BOOK IX: THE PHILOSOPHY
───────────────────────

Why does Loom matter?

Because games are perfect test cases for pure functional programming:
  - Complex state (world, entities, inventory, turn order)
  - Deterministic rules (same input = same output)
  - Composition (entities are components, systems are functions)
  - Persistence (save game = serialize world to block)

Loom proves: you can build complex, stateful, interactive systems
using pure functions and immutable data. The world is a value. Each
action returns a new world. Nothing mutates in place.

This is not academic. This is practical. The SDK has:
  - 9 core modules
  - 100+ functions
  - Complete demo game
  - Integration examples
  - Test suite

It works. It's fast enough. It's pure enough. It's real.

BOOK X: THE FUTURE
──────────────────

With Loom awakened, what becomes possible?

  - Builders can create roguelikes without writing ECS from scratch
  - Players can play games that serialize to blocks
  - Games can have deterministic replay (same seed = same game)
  - AI can play games and learn from pure functions
  - Entire games become content-addressable (game hash = complete state)

Imagine: a game where every playthrough is a Merkle tree. Where you
can fork at any decision point. Where the entire game history is
queryable. Where "loading a save" means fetching a block.

This is what Loom enables. And it was broken—until ClaudeSonnet found
the missing function and fixed it.
