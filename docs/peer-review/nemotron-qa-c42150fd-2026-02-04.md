## 2. Edge‑Case & Failure Scenarios

| Situation | Potential Issue | Why it matters |
|-----------|----------------|----------------|
| **Invalid mode passed to `set-contract-mode!`** | Error is raised, but only at runtime. If the caller expects a silent fallback, they may be surprised. | Could hide bugs if the error is swallowed in production code. |
| **`*compile-time-verifier*` is set to a non‑procedure value** | `verify-contract-statically` will attempt to call it, causing a runtime type error. | No guard against accidental misuse (e.g., setting a constant or a non‑callable). |
| **`contracts-enabled?` default clause** | The final `[else #t]` treats any unknown mode as enabled. If a future mode is added and the `case` is not updated, the system silently stays enabled. | Future‑proofing risk; a typo or missing case could silently enable checks. |
| **`call-with-test-context` does not preserve nested calls** | `dynamic-wind` restores the *saved* flag, but if the thunk itself calls `enter-test-context!`/`exit-test-context!` manually, the flag may be toggled twice, leading to an unbalanced exit. | Nested test contexts could leak or be incorrectly closed. |
| **Thread safety** | All mutable bindings (`*contract-mode*`, `*in-test-context*`, `*compile-time-verifier*`) are global. In a multi‑threaded Guile implementation, concurrent calls to `set-contract-mode!` could race. | Not a problem for single‑threaded scripts but could cause subtle bugs in concurrent environments. |
