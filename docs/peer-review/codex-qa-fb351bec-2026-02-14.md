## Correctness

- **[Critical] Response broadcast to all clients in session, not origin.** Client registration happens at `:249` and forwarding fanout at `:402`. This conflicts with request-id scope assumptions in `lattice/ipc/protocol.ss:33` and can cause cross-client response mixups/data leakage.
- **[High] Dead worker sessions not retired immediately.** Existing session records are always reused at `:225`, and write failures only send an error without removing/restarting the session at `:254`. Recovery is delayed until heartbeat cleanup.
- **[High] Long-running evals treated as dead workers.** Worker loop is single-threaded (`:220`) so it cannot answer ping during eval; daemon declares unresponsive after timeout at `:519` and kills.
- **[Medium] Session expiry decay logic effectively constant 600s** because of `max extension 600` at `:81`; defeats the decay intent in comments.
- **[Medium] Request validation partial.** `route-message!` checks session id but not request shape/id/expr type before forwarding at `:241`.

## Race Conditions

- Client disconnect races not surfaced to Scheme. Reactor removes connections internally (`ipc_reactor.rs:342`), but daemon keeps stale client ids and still "successfully" enqueues sends (`ipc_reactor.rs:619`), silently dropping later.
- PID reuse risk in escalation path: daemon tracks PIDs regardless of TERM success at `:427`, then later does `kill -0`/`kill -KILL` at `:443`. A reused PID can be killed incorrectly.
- Graceful shutdown always followed by TERM at `:483`, even after ack; this widens the PID reuse window.

## Resource Leaks

- **Worker child reaping missing.** Worker spawned via `open-process-ports` at `:217`, no wait/reap path. Reviewer verified defunct children occur in practice.
- **`session-client-ids` only grows**; no pruning on disconnect at `:249`.
- **Worker stderr pipe retained but never drained.** Daemon stores it at `:49` but does not read it, while worker writes startup/diagnostic output to stderr. Can block worker on full pipe.

## Robustness

- Main loop polls only one inbound client message per tick at `:603`, creating avoidable queue latency under load.
- Heavy use of `guard ... #f` suppresses actionable failure signals at `:384`, `:500`.
- Frame buffer accumulation copy-heavy (`bytevector-append` at `:319`), O(n²) across chunked large frames.
- Crash-loop handling is threshold gating, not true backoff, and does not throttle repeated spawn failures before `record-spawn!` at `:210`, `:219`.

## Style

- Unused/legacy fields: `*worker-timeout*` at `:29`, `session-last-request` accessor at `:63`.
- Session records as positional mutable lists at `:54` are brittle; a record type would be safer/readable.
- Comments and behavior diverge in decay extension logic at `:76` vs actual effect.

## Recommendations

1. Replace broadcast routing with per-request routing map `(session-id, req-id) -> client-id`; forward responses only to origin.
2. Add disconnect observability from reactor (event queue or `ipc-send!` returning ENOENT) and prune `session-client-ids`.
3. Implement proper child reaping (waitpid/process API) and avoid zombie accumulation.
4. Redesign heartbeat semantics: do not classify worker as dead while request is in-flight; use separate "last-progress" metrics.
5. Drain or redirect worker stderr (dedicated reader thread, file log, or `/dev/null`).
6. Drain inbound queue each tick (loop `ipc-poll-next` until empty), not one-message-per-iteration.
7. Harden termination: track TERM success, avoid unconditional escalation, and protect against PID reuse.
8. Add tests for multi-client routing isolation, disconnect pruning, long-running eval heartbeat behavior, stderr backpressure, and zombie prevention.
