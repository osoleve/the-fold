  Purpose: Connects to outside world

  ┌─────────────────────────────────────┐
  │              user/                  │  Applications, experiments
  ├─────────────────────────────────────┤
  │              shell/                 │  ALL impure code lives here
  ├─────────────────────────────────────┤

  The Pattern
  Pure Definition: stdlib/graphics/ — colors, shapes, transforms
  Impure Realization: shell/ui/ — render to terminal/files
  ────────────────────────────────────────
  Pure Definition: stdlib/query/sql/ — parse, validate, format
  Impure Realization: shell/db/ — execute against real DB
  ────────────────────────────────────────
  Pure Definition: stdlib/physics/ — simulate, compute
  Impure Realization: shell/media/ — export animations
  ────────────────────────────────────────
  Pure Definition: core/blocks/ — CAS operations
  Impure Realization: shell/storage/ — persist to disk
  Why Not Split stdlib?

  1. Complexity — "which stdlib do I load?" becomes a question
  2. Purity boundary bleeds — tempting to make exceptions
  3. Shell already exists — it's the designated impure zone
  4. Testing — pure stdlib is trivially testable; shell needs mocking

  Shell Structure (expanded)

  shell/
  ├── repl/           # REPL, sessions (IO for core/lang)
  ├── storage/        # CAS persistence (IO for core/blocks)
  ├── io/             # File system, JSON
  ├── git/            # Git operations
  ├── ui/             # Graphics rendering (IO for stdlib/graphics)
  ├── db/             # Database connections (IO for stdlib/query)
  ├── media/          # Export audio/video (IO for stdlib/physics, music)
  ├── net/            # Network (future)
  └── ...

  The rule becomes simple: if it touches the outside world, it's shell/. Everything else is pure and goes in core/ (language) or stdlib/ (library).

  (import (stdlib total linalg vec))      ; OK
  (import (stdlib partial physics))        ; ERROR - not total
  (import (stdlib effect random))          ; ERROR - has effects

  ;; In shell/ - anything goes
  (import (stdlib total linalg vec))       ; OK
  (import (stdlib partial physics))        ; OK  
  (import (stdlib effect io))              ; OK

  The Boundary Question

  Where does partial/ end and effect/ begin?

  - partial/: Pure computation that might not terminate → solvable with fuel
  - effect/: Observably interacts with outside world → cannot be made pure

  A physics simulation is partial (might run forever) but pure (deterministic, no IO). Random number generation is effect (needs seed from outside or maintains hidden state).

  The Implicit Stdlib

  "Stdlib" becomes a computed property, not a directory:

  ;; stdlib = tree nodes whose only dependency is core
  (define (stdlib? node)
    (null? (tree-dependencies node)))

  ;; Or by DAG depth
  (define (tier node)
    (if (null? (tree-dependencies node))
        0
        (+ 1 (apply max (map tier (tree-dependencies node))))))

  - Tier 0 = foundational (the "stdlib")
  - Tier 1 = builds on foundations
  - Tier N = N levels deep

  What This Enables

  1. No artificial boundary — everything is just the tree
  2. Stdlib evolves naturally — if a tier-2 module becomes foundational, refactor its deps and it "becomes" stdlib
  3. Curriculum is the DAG — topological sort gives you the learning order
  4. Badges propagate — if all your deps are total, and you're total, you inherit "total" badge

  The total/partial/effect Split

  Still needed, but as metadata not directories:

  ;; In index.sexp
  (skill linalg/vec
    (tier 0)
    (purity total)        ; pure and terminates
    (fuel-bound "O(n)")
    (deps ()))

  (skill physics/simulate
    (tier 2)
    (purity partial)      ; pure but needs fuel
    (fuel-bound "O(n²)")
    (deps (linalg/vec linalg/matrix autodiff/reverse)))

  (skill io/file
    (tier 0)
    (purity effect)       ; impure
    (deps ()))

❯ lattice? 

● Yes. A lattice has:
  - Partial ordering (dependencies)
  - Multiple paths (DAG, not tree)
  - Mathematical resonance (meets, joins)
  - Growth connotation (trellis, things climbing)

  the-fold/
  ├── core/                    # Ring 0: Language kernel
  │   ├── base/
  │   ├── blocks/
  │   ├── types/
  │   └── lang/
  │
  ├── shell/                   # Ring ∞: Impure boundary
  │
  ├── lattice/                 # The verified skill lattice
  │   ├── index.sexp           # DAG structure, badges, deps
  │   │
  │   ├── linalg/              # Tier 0 (foundational)
  │   ├── data/

  │   ├── graphics/
  │   └── ...
  │
  └── .store/                  # Content-addressed backing

  And the import syntax writes itself:
